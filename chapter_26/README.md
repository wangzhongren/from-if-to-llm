# 第 26 章：真正的 tokenizer

## 本章的问题

第 25 章最后留下一句话：**我们的分词太粗糙。**

回头看我们一直用的办法：一个字一个 token。这在前面 24 章里一直很好用，
因为它简单到不需要解释。但它有两个躲不掉的毛病。

第一个毛病和词表有关。我们用第 1 章那张手写的词表试了一下"苹果不好吃"：

```text
苹果不好吃 -> ['苹果', '<UNK>', '好吃']   <- 有生词！
```

一个"不"字，让整句话的意思反了过来，而它在词表里根本不存在。
更让人不安的是，连第 1 章自己的句子都躲不过：

```text
苹果芯片很强 -> ['苹果', '芯片', '很', '<UNK>']  <- 有生词！
```

词表里有"很"、有"甜"、有"好吃"，就是没有"强"。因为**这张表是人写的，人写不全**。

第二个毛病是：如果我们想写得全一点呢？

```text
  我们的语料一共 5407 个字。
  语料里不同的 1 字片段：50 个
  语料里不同的 2 字片段：88 个
  语料里不同的 3 字片段：141 个
  语料里不同的 4 字片段：191 个
  语料里不同的 5 字片段：298 个

  语料越大，新片段就越多，词表跟着一直长。理论上的上限更吓人：
  常用汉字 3000 个，1 字组合最多有 3,000个
  常用汉字 3000 个，2 字组合最多有 900 万个
  常用汉字 3000 个，3 字组合最多有 270 亿个
  常用汉字 3000 个，4 字组合最多有 81 万亿个
```

第 2 章那个"几万个 if"的噩梦，换了一件衣服又回来了。

**顺便回答一个你可能早就想问的问题：第 1 章为什么只教"把句子拆成词"，
不讲 BPE、不讲子词、不讲字节？**

因为第 1 章的你还没有遇到这两个问题。那时候语料只有十句话、词表只有 16 个词，
"拆成词"是唯一不会出错的做法。**一个机制要在它的痛出现之后才好理解。**
如果你一上来就被告知"BPE 是子词分词算法"，你会记住这个词，但不知道它在救什么火。
现在你知道它要救什么了：一个是生词，一个是词表爆炸。

## 最简单的尝试

最直觉的修法：把词表写大一点。

这也是所有中文分词工具最早的做法——找一本词典，收几十万个词，拿它去句子里切词
（`before.py` 里的 `word_tokenize` 干的就是这件事：从当前位置开始，尽量匹配最长的词）。

它确实比字符级好：token 数少，语义完整，"苹果很甜"只要 3 个 token。
但词典这条路有个死结：

- 词典里的词，永远比语言里的词少。新词每天都在出现（"直播带货"、"折叠屏"），
  词典跟不上，跟上了也没法覆盖专业名词、人名、错别字、表情。
- 词典越大，生词的代价越大：一个不在词典里的字，整句话都受影响。
- 而且词典是"人定的"。我们希望这个词表是**从语料里自己长出来的**。

那有没有一种办法：**词表大小由我们定，既不写词典，也不会有生词？**

## 实验

`after.py` 里有一个能跑的 mini-BPE，`experiment.py` 把它和另外三种分词法摆在一起比。

### 四种分词法，切同一批句子

```text
苹果不好吃
  字符级    5 个  ['苹', '果', '不', '好', '吃']
  词级      3 个  ['苹果', '<UNK>', '好吃']   <- 1 个生词
  BPE       3 个  ['苹果', '不', '好吃']
  字节版    5 个  ['苹果', '�', '�', '�', '��吃']

苹果很甜
  字符级    4 个  ['苹', '果', '很', '甜']
  词级      3 个  ['苹果', '很', '甜']
  BPE       2 个  ['苹果', '很甜']
  字节版    1 个  ['苹果很甜']

华为发布新平板
  字符级    7 个  ['华', '为', '发', '布', '新', '平', '板']
  词级      5 个  ['华为', '发布', '新', '<UNK>', '<UNK>']   <- 2 个生词
  BPE       4 个  ['华为', '发布新', '平', '板']
  字节版    8 个  ['华为', '发布新', '�', '�', '�', '�', '�', '�']

我昨天在商场看到苹果刚刚发布的新手机
  字符级   18 个  ['我', '昨', '天', '在', '商', '场', '看', '到', '苹', '果', '刚', '刚', '发', '布', '的', '新', '手', '机']
  词级     15 个  ['<UNK>', ..., '苹果', '<UNK>', '<UNK>', '发布', '<UNK>', '新', '手机']   <- 11 个生词
  BPE       2 个  ['我昨天在商场看到', '苹果刚刚发布的新手机']
  字节版    7 个  ['我昨天在商场看到', '苹果', '刚', '刚', '发布', '的新', '手机']

（字节版里的 '�' 是半个字的字节：那个字在训练语料里没出现过，
  所以 BPE 还没学会把它粘起来。字节版永远切得开，但可能切得难看。）
```

注意那两句长句：词级分词在它身上吐了 11 个 `<UNK>`，因为那句话里的虚词
（"我""昨天""在"）压根不在第 1 章那张表里。**我们的语料一直在变复杂，
手写词表的能力却一直停在原地。**

### BPE 的全过程

BPE 训练完会留下一串"我是怎么长大的"记录。前 20 次合并长这样：

```text
前 20 次合并（学到的第一批 token）：
  苹果  发布  。苹果  。小  手机  发布新  很强  好吃  华为  芯片  。小米  这个  这个苹果  。这个苹果  。华为  电脑  香蕉  。香蕉  考试  给了
```

再合并 40 次，就开始出现更长的片段：

```text
第 40-60 次合并（开始出现更长的片段）：
  发布的新手机  刚发布的新手机  刚刚发布的新手机  。小王把书给了小李因为他明天考试  。我昨天在商场看到  很好吃  真甜  成派  做成派  。小米发布新  很甜  。苹果发布新  芯片很强  真好吃  。华为发布新  电脑很强  手机很强  。苹果很好吃  苹果刚刚发布的新手机  。我昨天在商场看到苹果刚刚发布的新手机
```

### BPE 的旋钮只有一个

```text
合并次数    词表大小    语料总 token 数   这句话几个 token
------------------------------------------------------------------------
0           50          5,407             18
50          100         1,494             3
100         150         580               2
200         250         379               2
500         550         79                2

合并得越多：词表越大、序列越短。
词表大 = 输出层的矩阵大；序列短 = 模型要算的位置少。这就是分词要权衡的东西。
```

### 没有人告诉它什么是"词"

```text
第 1 章那张词表里，长度大于 1 的词有 11 个：苹果  发布  手机  芯片  电脑  华为  小米  好吃  香蕉  这个  做成
其中被 BPE 自己合并出来的：9 个 -> 苹果  发布  手机  芯片  电脑  华为  好吃  香蕉  这个

没有人告诉 BPE 中文的词长什么样。它只知道'哪两个 token 老挨在一起'。
结果它把'苹果''发布''手机''好吃'这些片段拼了出来 —— 因为它们确实老挨在一起。
```

11 个词里,它自己拼出来了 9 个。剩下两个没拼出来（"做成""这个"），
是因为它们在我们的语料里出现的次数还不够多——BPE 只认频率，不认语法。

## 新机制

**BPE（Byte Pair Encoding，字节对编码）。** 名字听起来很怪
（它本来是 1994 年一篇数据压缩论文里的算法），但做的事只有一句话：

> 一开始，每个字符就是一个 token。
> 然后反复做一件事：**找出当前最常挨在一起的两个 token，把它们粘成一个新 token。**

粘一次，词表就多一个 token。粘多少次由我们定。

```
我要多大词表？
    词表大小 = 最初的字符数 + 合并次数

所以：合并 200 次，词表就是 50 + 200 = 250 个 token。
```

用伪代码写出来只有三行：

```python
for _ in range(合并次数):
    找到出现次数最多的相邻对 (a, b)
    把序列里所有的 a b 换成 ab
```

**为什么它解决了刚才那两个问题？**

- **没有生词**。最坏的情况就是"一个 token 都没合并上"，退回成一个个字符。
  而字符表是从语料里数出来的，**一定够用**。
- **词表大小可控**。词表不再由"语言里有多少词"决定，而由"我们想合并多少次"决定。
  想要 5 万 token 的词表？合并 5 万次。想小一点？少合并几次。

**BPE 的谱系。** 到这里可以把分词这件事的四种做法排一排：

| 做法 | 最小单位 | 词表怎么来 | 生词 | 序列长度 |
|---|---|---|---|---|
| 字符级 | 字 | 语料里出现过的字 | 没有（但每个字都要单独学） | 最长 |
| 词级 | 词 | 人手写的词典 | 有 `<UNK>` | 最短 |
| **BPE** | 字 → 合并出来的片段 | 从语料里合并出来 | 没有 | 中等 |
| **byte-level BPE** | 字节（0–255） | 从 256 个字节合并出来 | 没有，任何文本都能编码 | 中文偏长 |

最后一种值得单独说。GPT-2 之后的模型用的是字节版：**连"字符"这个概念都不预设了**，
直接把文本看成一串 0–255 的字节。好处是任何东西（繁体字、生僻字、emoji、代码、二进制噪声）
都能编码，永远不会有 `<UNK>`。代价是中文一个字要占 3 个字节，
要花一部分合并预算去把"一个字的三个字节"粘起来：

```text
合并次数      字符版 token 数       字节版 token 数       
----------------------------------------------------------------
0         7                 21                
50        3                 4                 
200       3                 3                 
```

看第一行：还没合并的时候，字节版是字符版的 3 倍长。合并多了以后就追回来了。

（实现上，字节版和字符版**是同一份代码**，改的只是"最小单位"是什么——
`after.py` 里 `train_bpe(text, 次数, unit=to_bytes)` 就切过去了。）

## Python 实现

`after.py` 一共三个函数，就是 BPE 的全部。

**第一步：数相邻对。**

```python
def count_pairs(tokens):
    """数一数：相邻的两个 token 一起出现了多少次。"""
    pairs = {}
    for left, right in zip(tokens, tokens[1:]):
        pairs[(left, right)] = pairs.get((left, right), 0) + 1
    return pairs
```

**第二步：合并。**

```python
def merge_pair(tokens, pair):
    """把序列里所有的 `pair` 合并成一个 token：A B -> AB。"""
    merged = []
    position = 0
    while position < len(tokens):
        if (position < len(tokens) - 1
                and tokens[position] == pair[0] and tokens[position + 1] == pair[1]):
            merged.append(pair[0] + pair[1])
            position += 2
        else:
            merged.append(tokens[position])
            position += 1
    return merged
```

**第三步：循环。**

```python
def train_bpe(text, num_merges, unit=None):
    tokens = unit(text) if unit else list(text)
    merges = []
    for _ in range(num_merges):
        pairs = count_pairs(tokens)
        if not pairs:
            break
        best = max(pairs.items(), key=lambda item: (item[1], item[0]))[0]
        merges.append(best)
        tokens = merge_pair(tokens, best)
    return merges
```

`merges` 这个列表就是训练的全部产物：**一串有顺序的合并规则**。
它同时也就是词表——第 i 条规则产生的新 token，就是词表里的第 i 个新成员。

**编码**就是把这串规则按顺序用一遍：

```python
def encode(text, merges, unit=None):
    tokens = unit(text) if unit else list(text)
    for pair in merges:
        tokens = merge_pair(tokens, pair)
    return tokens
```

为什么按顺序用一遍就等于"重新合并一遍"？因为一条规则只可能出现在它之前那些规则
制造的上下文里——所以从第一条开始用，一定是对的。

**解码**更简单：因为每次合并只是把两个 token 粘在一起，所以拼起来就还原了。

```python
def decode(tokens):
    return "".join(tokens)
```

`decode(encode("苹果发布新手机")) == "苹果发布新手机"` 这条性质，测试里是必须过的。

## 它解决了什么

- **词表大小变成可调的了**。合并 200 次 → 词表 250 个；合并 500 次 → 词表 550 个。
  我们不再需要手写词典。
- **生词问题消失了**。"苹果不好吃"在词级分词下是 `['苹果', '<UNK>', '好吃']`，
  在 BPE 下是 `['苹果', '不', '好吃']`——"不"这个字在训练语料里一次都没出现过，
  BPE 还是把它切了出来，因为它最差也能退回字符。
- **序列变短了**。那句 18 个字的长句，从 18 个 token 变成 2 个 token（同一段文本，
  模型要算的位置少了一个数量级）。第 22 章那个模型跑不动长句子，一半的原因是分词太长。
- **没有人告诉它什么是词**，它自己从频率里把"苹果""发布""手机""好吃"这些片段
  拼了出来（第 1 章那张 11 个词的词表里，它自己长出来了 9 个）。

## 它还解决不了什么

分词这件事到这里基本交代完了。但请注意：**BPE 只是让文本变成一串编号，
它一点也没有让模型变聪明。**

现在把我们的模型和 GPT 摆在一起，一项一项看：

| | 我们的模型（第 22/25 章） | GPT |
|---|---|---|
| 分词 | 字符级（这一章刚升级成 BPE，但模型还没用上） | byte-level BPE，5 万 token |
| 每个 block 的归一化 | 先算完再加、再 LayerNorm | 先 LayerNorm 再算 |
| MLP 的激活函数 | ReLU | GELU |
| 位置信息 | 第 16 章的固定正弦编码 | 一张可学习的位置表 |
| 层数 × 维度 | 2 层 × 32 维 | 96 层 × 12288 维 |
| 参数量 | 27,812 | 1750 亿 |

右边那一列里，有几项我们从没写过：先 LayerNorm 再算、GELU、可学习的位置表。
它们是不是什么我们还不知道的新机制？还是老东西换了个用法？

下一个问题就是：**GPT 里到底有没有我们没写过的模块？**
