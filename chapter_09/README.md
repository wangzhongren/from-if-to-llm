# 第 9 章：让机器自己算梯度

## 本章的问题

上一章最后，我们的网络长这样：

```text
输入 -> 中间层（relu）-> 输出 -> softmax -> loss
```

它的梯度是我们拿链式法则一段一段推出来、一行一行写下来的：
输出层的误差、中间层的误差、relu 的那个开关，一处一处手写。

两层还撑得住。所以这一章我们做的第一件事，是把网络堆到三层 ——
不是因为它需要三层，而是因为我们要看清"多一层"要付什么代价。
三层的情况下，这些手写的东西有这么多：

```text
前向 forward：25 行
反向 backward：55 行
一共 80 行，全是人手写的。
```

而且每加一层，都要：

1. 重推一遍链式法则（3 层是 2 段"误差乘权重"，4 层就是 3 段）；
2. 重写一段带下标的代码；
3. 用第 6 章的数值法回头验一遍 —— 因为写错了不会报错，只会安静地越学越差。

我们真的验了，而且这次侥幸没错：

```text
        参数           手写的梯度          数值法的梯度           差
  w1[0][1]     -0.00384526     -0.00384526    7.01e-12
  ...
最大的差是 7.01e-12 —— 这次侥幸是对的。
```

"侥幸"两个字很重。人推的公式，对和错只差一个下标，而错了没人告诉你。

**这就是第 8 章留下的问题。这一章我们不改损失、不改结构，只改一件事：
梯度是谁算的。**

## 最简单的尝试

在发明新东西之前，有两个显而易见的办法。我们都试过了。

**办法一：继续手写。**

就是 `before.py`。它能跑，loss 能降，准确率 100%。
但上面那张表已经说清楚了：三层 80 行，四层更多，
九十层不敢想。

**办法二：干脆不写，用数值法。**

第 6 章的数值梯度是万能的：它只认 loss 这一个数字，
管你里面是几层、有没有 relu。换任何结构它都能用，而且绝对正确。

代价是它的速度：

```text
每算一个参数的梯度，要把整个模型重跑两遍。
```

我们有 22 个参数，那一步就是 44 遍。参数多一点呢？
GPT-3 有 1750 亿个参数，一步要跑 3500 亿遍前向计算。

这条路也堵死了。

**一条路要人推，一条路要硬算。两条都走不通，只能换一个想法：**

> 能不能让程序在算的时候，自己把"该怎么求导"记下来？

8.67e-11 —— 这是浮点数的误差范围，不是"差不多"。

两边会对不上 —— 那不是引擎错了，是数值法在折点上本来就没有定义。
这类"看起来像 bug 其实是我自己站错地方"的情况，以后还会遇到。）

## 新机制

### 先在一个最小的例子上，把道理说清楚

不看代码，先看三个数：

```text
a = 2, b = 3, c = 4

d = a * b        -> 6
e = d + c        -> 10
```

现在问：`e` 对 `a`、`b`、`c` 分别有多敏感？

正向走完，我们手里只有一个 `e = 10`。往回走：

```text
e 对自己的梯度 = 1

e = d + c ：
    加法把梯度原样分给两边
    d.grad += 1
    c.grad += 1

d = a * b ：
    乘法把梯度乘上"对方的数值"，再送出去
    a.grad += b * d.grad = 3 * 1 = 3
    b.grad += a * d.grad = 2 * 1 = 2
```

结果：`a.grad = 3`，`b.grad = 2`，`c.grad = 1`。

验算一下：把 `a` 从 2 改成 2.001，`e` 会从 10 变成 10.003。
**变了 0.003，正好是 `a.grad × 0.001`。**

现在请注意一件很关键的事：

> 回退的每一步，只用到两样东西 ——
> **这个运算是什么**，以及**它的输入当时是多少**。
>
> 这两样东西，在正向计算的时候全都知道。

所以我们不需要推任何公式。只要在正向算的时候顺手记一笔，
反向就能自己走回去。这就是这一整章的全部思想。

### 计算图：每一步都记一笔

把上面那个式子里的每一个中间结果都当做一个节点，
画出来就是一张图：

```text
     a(2)   b(3)
        \   /
   d = a*b(6)   c(4)
          \    /
      e = d+c(10)
```

这张图叫**计算图**。

在代码里，"记一笔"是这么做的：

```python
def __mul__(self, other):
    out = Value(self.data * other.data, (self, other), "*")
    #                              ^^^^^^^^^^^^^ 记下来路

    def _backward():
        self.grad += other.data * out.grad
        other.grad += self.data * out.grad

    out._backward = _backward     # 记下"该怎么把梯度还给我的输入"
    return out
```

每个节点身上挂着一个小函数。这个小函数是**在正向计算的时候**就被写好的，
它记着当时那两个数（`self.data` 和 `other.data`）是多少。

所以 `backward()` 要做的事情，简单到不像话：

```python
def backward(self):
    self.grad = 1.0
    for node in reversed(拓扑排序的结果):
        node._backward()
```

从 loss 出发，把自己那点梯度沿着图倒着送回去。
每个节点只负责一件事：**把收到的梯度，按自己那个算子的规矩，分给输入。**

### 拓扑排序：为什么不能顺着图随便走

如果只是"从 loss 出发，遇到一个节点就调用它的 `_backward`，
再递归到它的输入"，有一类图会算错。

错在哪里？看这张图：

```text
a(2)
├──> b = a * 3
│      ├──> c = b * a
│      └──> d = b + c
```

`b` 有两个下游：`c` 和 `d`。这两条路都会往 `b.grad` 上加东西。

如果我们在 `c` 还没把梯度给到 `b` 的时候，就先跑了 `b._backward()`，
那 `b` 会按一个偏小的值往下传 —— 传出去的值就再也补不回来了。

（这个错误是可以用代码复现的，见 `exercises.md` 第 3 题：
正确答案是 15，不排序跑出来是 18。）

**所以必须先排一个序：保证轮到任何一个节点的时候，
它的所有下游都已经算完了。**这就是拓扑排序要存在的原因。

代码里一共 8 行：

```python
def build(node):
    if id(node) in visited:
        return
    visited.add(id(node))
    for child in node._prev:      # 先把所有上游走完
        build(child)
    order.append(node)            # 再把自己放进去

build(self)
for node in reversed(order):      # 倒着走
    node._backward()
```

这是一个后序遍历：先走完所有的父节点，再记录自己。
排出来的顺序保证"父节点一定在子节点后面"，
于是倒着走的时候，每个节点轮到它时，梯度一定已经收齐了。

### 梯度是"加"上去的，不是"覆盖"的

这是这一章最重要的一段，请慢一点看。

`_backward` 里写的是 `+=`，不是 `=`：

```python
def _backward():
    self.grad += other.data * out.grad
    other.grad += self.data * out.grad
```

为什么？

因为**一个节点可能有多条路径通到 loss**。

最简单的例子：`x * x`。这里的 `self` 和 `other` 是同一个对象，
两条路径都通到同一个 `x`：

```text
x(3) ──┬──> x * x (9)
       └──┘
```

`x` 变了，`x * x` 的两边都变了。所以 `x` 对结果的贡献是两边之和：
`3 + 3 = 6`，正好是 `2x`。

如果把 `+=` 写成 `=`，后一条路径会把前一条盖掉，答案就是 3 —— 错的。

现实里这种情况到处都是。比如同一个词在一句话里出现了两次，
那条权重就会被用到两次，两条路径上的梯度当然要加起来。

**代价是什么？**

代价是：`backward()` 是"攒"的，不是"重置"的。
你连着调用两次，同一个梯度就会被加两次。

实验第 4 步亲眼看到了：

```text
一次 backward 之后: [ 0.2515 -0.2642  1.2808  0.2098]   （正好是 2a）
再来一次 backward : [ 0.5029 -0.5284  2.5617  0.4196]   （变成了 4a）
```

所以每一轮训练，**必须先把上一轮的梯度清零**：

```python
for p in params:
    p.zero_grad()
loss.backward()
```

忘了清零，梯度会一轮一轮累积起来，训练会越来越疯，
而程序不会给你任何提示。

**PyTorch 的行为和这一模一样**，这就是为什么每个 PyTorch 教程里
都会出现 `optimizer.zero_grad()`。

（回头看第 6 章的数值法：它每算一次梯度，都是重新把 loss 算两遍，
算完就扔，所以它从来没有这个问题。自动求导为了快，把梯度攒着，
代价就是清零这件事得由你负责。）

### 给它一个名字

这套东西叫**自动求导**（autograd）：

> 每一次运算都顺手记下"我是怎么来的"和"该怎么回去"，
> 需要梯度的时候，从结果出发沿着记录倒着走一遍。

- 计算图：正向计算时自动记下的那张网。
- `backward()`：沿着计算图把梯度从结果送回参数。

## Python 实现

`after.py` 里有一个完整的、自包含的标量版引擎，一共 130 行左右，可以一口气读完。
它只有一个类：

```python
class Value:
    def __init__(self, data, _children=(), _op=""):
        self.data = float(data)
        self.grad = 0.0
        self._backward = lambda: None      # 叶子节点：没有上游
        self._prev = tuple(_children)      # 我是用谁算出来的
        self._op = _op                     # 用什么算子
```

加上 `+ - * / **`、`exp`、`log`、`relu`，每个算子各自带一个小 `_backward`，
再加上那个 8 行的 `backward()`。

用它的训练代码长这样：

```python
def forward(params, x):
    """三层。中间两层算完都过一遍 relu。

    整个函数里没有一行字是在算梯度 —— 它只是在做乘法和加法。
    """
    layer1 = [...]
    layer2 = [...]
    return scores
```

```python
for _ in range(steps):
    for p in flat:
        p.grad = 0.0          # 梯度是累加的，每一步开始前必须清零
    loss = batch_loss(params, data)
```

对比一下 `before.py`：同样是三层网络，那里有 55 行手写的 `backward`。
这里一行都没有。

**那完整的数组版呢？**

标量版一次只能算一个数。真实的模型里一次要算几十万个数字。
所以仓库根目录的 `toygrad/tensor.py` 里有一份数组版：

- 把 `float` 换成 `numpy` 数组；
- 把 `self.grad += other.data * out.grad` 换成逐元素的数组乘法；
- 多了一些数组才需要的算子（矩阵乘法、广播对齐、softmax、查表……）。

**道理一个字都没变。** `experiment.py` 用的就是那一份，
它和数值法对上的结果你已经看到了。

`after.py` 里还留了一处伏笔：那个 `Value` 类的写法和 PyTorch 里
`torch.Tensor` 的设计是一一对应的 —— `data`、`grad`、`backward()`、
`zero_grad()`，连名字都一样。

## 它解决了什么

- 三层网络，梯度代码从 55 行变成 **0 行**。
- 加一层、改一层、把 relu 换成 tanh —— **梯度代码都不用动**。
  因为梯度不是我们写的，是算出来的。
- 自动求导的结果和第 6 章的数值法完全一致（22 个参数，最大差 8.67e-11）。
- 同一个引擎用回第 6 章的句子分类任务，10 句话全部分对。
- 我们不用再"怕写错"了。写错了会被数值法当场抓住 ——
  而手写的公式，错了只会安静地越学越差。

更长远一点说：第 7 章我们有了"层"，第 8 章我们有了"拐弯"，
这一章我们有了"不用手推梯度"。

**这三样加起来，才轮到"想堆多少层就堆多少层"这件事成立。**
后面所有的模型 —— 包括第 22 章那个小 GPT，包括 GPT-3 ——
都是靠这三样东西堆出来的。

### 顺便说清楚：PyTorch 的 `loss.backward()` 到底干了什么

现在你写的 `loss.backward()`，做的就是这么几件事：

1. 正向计算的时候，每一个 `requires_grad=True` 的张量都被记进了一张计算图；
2. `backward()` 从 `loss` 出发，先把它自己的梯度设成 1；
3. 沿着图倒着走，每个算子把自己那份梯度算出来，**累加**到输入的 `.grad` 上；
4. 走完之后，每个参数的 `.grad` 就摆在那里，等着 `optimizer.step()` 来读。

和你在 `after.py` 里写的那个 `Value` 唯一的区别是：
PyTorch 的算子是数组版的、在 GPU 上跑、而且有一千多个。
**原理一模一样。**

所以：`optimizer.zero_grad()` 为什么必须写？
因为第 3 步是累加。这就是这一章从头到尾在讲的那件事。

## 它还解决不了什么

实验第 5 步里，我们把这个引擎用回了那 10 句话，10 句全对。
但输出里藏着这一章真正的问题：

```text
它学到的权重（科技那一类）：
    苹果  第  0 号  权重  -0.234
    发布  第  1 号  权重  +1.156
     新  第  2 号  权重  +1.039
    芯片  第  4 号  权重  +1.874
    好吃  第  8 号  权重  -1.277
    甜    第 10 号  权重  -1.131
```

第 0 号、第 1 号、第 2 号 —— 这些编号是我们在第 1 章随手排的。

我们喂给模型的输入，是一个 16 维的计数向量：
第 0 个位置是"苹果"出现了几次，第 1 个位置是"发布"出现了几次……
模型从来没见过"苹果"这两个字，它看到的只有"第 0 号位置上的数字"。

那么问题来了：

- "苹果"是第 0 号，"香蕉"是第 11 号。这两个编号有什么关系吗？
- 没有。0 和 11 之间没有"水果"的意思，也没有"能吃"的意思。
- 如果我们第 1 章把词表顺序换个排法，"苹果"变成第 7 号，
  模型学出来的东西会变吗？**一点都不会。**

对模型来说，"苹果"和"香蕉"之间的差别，
和"第 0 号位置"与"第 11 号位置"之间的差别，是同一件事 ——
**它们只是编号，编号本身没有任何意义。**

我们现在有了一台很好用的引擎，可以算任何东西的梯度。
但它算出来的梯度，是相对于"编号"的梯度。
编号里没有意义，那它学到的到底是什么？

**下一章要问的是：一个词，除了编号，还能用什么来表示？**
