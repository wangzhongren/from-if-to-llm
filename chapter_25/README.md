# 第 25 章：用 PyTorch 重写我们的模型

## 本章的问题

上一章最后留下了一个问题：**玩具模型为什么这么弱。**

第 24 章我们把模型翻来覆去看了个遍，它该有的零件都有了：词向量、位置、注意力、残差、
LayerNorm、MLP、输出层。它只是小得可怜——2 层、3 万个参数，而对面那个能聊天的东西
有几千亿个参数。

那就把它做大。可是在动手之前，我们先试了一下。

## 最简单的尝试

最直觉的做法：我们的引擎不是能跑吗？把数字改大一点不就行了？

`before.py` 就是这么干的。先把第 22 章那个小模型的参数改大一点点：

```python
small = OurModel(VOCAB_SIZE, dim=32, n_layer=2, n_head=4, block_size=16, seed=0)
big   = OurModel(VOCAB_SIZE, dim=128, n_layer=4, n_head=4, block_size=32, seed=0)
```

`dim` 从 32 到 128，层数从 2 到 4，参数量从 2.7 万涨到 80 万——大了 29 倍，
但离 GPT-3 还差 20 万倍。

跑起来是这样的：

```text
一、第 22 章的大小：dim=32，2 层
----------------------------------------------------------------
参数量：27,492
训练 200 步，用时 0.31 秒（1.6 毫秒/步）
loss 变化：3.578  3.041  1.697  0.379  0.246

二、第 24 章说的'做大一点'：dim=128，4 层
----------------------------------------------------------------
参数量：800,292（比上面大 29 倍）
只跑了 5 步，用时 0.19 秒（38 毫秒/步）
内存：169 MB -> 870 MB，5 步涨了 701 MB

时间还能忍：训练 200 步只要 8 秒。
内存不能忍：按每步 140 MB 的速度，200 步要 28,215 MB。

原因：为了 backward，我们的引擎要记住图上每一个中间张量。
每一个中间张量都是一整个 float64 的 numpy 数组，一步算完它们不会退回去。
GPT-3 有 1750 亿参数，是我们这个模型的 218,670 倍。
就算时间和内存只按参数量线性增长：一步要 138 分钟，
一步要吃掉 31 TB 内存。这条路走不通。
```

问题不在"跑不动"，而在**跑不快、也放不下**。

我们的引擎为了能 backward，必须记住计算图上每一个中间张量的数值（第 9 章就是这么设计的）。
一个 80 万参数的模型，每一步要吃掉 140 MB，而这些内存要等 Python 把整张图回收掉才还回来。
模型再大十倍，就是每步 1.5 GB；大一百倍，这台机器直接趴下。

所以要做大模型，先得换一台真正的发动机。

## 实验

换发动机之前，我们得先确认一件事：**换了以后，算出来的东西还是同一个东西吗？**

（下面贴的都是实跑输出。**loss、准确率、参数量这些数字是固定的**——我们把随机种子写死了；
**时间和内存会有浮动**（同一台机器上时间差 10%、内存差几 MB 都正常），
你跑出来的可能和这里不完全一样。）

`experiment.py` 做了四个实验。

### 实验一：同一份权重，两个引擎算出同样的分数吗？

把 `before.py` 那个引擎里的参数（numpy 数组）原样灌进 PyTorch 模型，喂同一句话：

```text
输入形状 (8, 16)，输出形状 (8, 16, 36)（每个位置 36 个分数）
两条输出的最大差值：5.46e-08
（差的这一点来自 float32 和 float64 的舍入，不是算错了）
```

差值是 `5.46e-08`。不是"差不多"，是"同一件事"。

### 实验二：同一起点、同一份数据、同一个种子，各训练 100 步

```text
步数    我们的引擎    PyTorch       差值
----------------------------------------------------------------
10      3.2902        3.2902        0.00000
20      3.2823        3.2823        0.00000
30      3.0938        3.0938        0.00000
40      2.9906        2.9906        0.00000
50      2.6217        2.6217        0.00000
60      2.3389        2.3389        0.00000
70      2.1182        2.1182        0.00000
80      1.8654        1.8654        0.00000
90      1.5900        1.5900        0.00000
100     1.0396        1.0396        0.00000
```

两条 loss 曲线在 100 步里几乎没有分开过。连 Adam 的更新量都对得上——
因为 PyTorch 的 `Adam` 和我们第 22 章写的那个，本来就是同一个算法。

### 实验三：PyTorch 连注意力都封装好了

我们第 14、15、21 章写了几十行的多头注意力，在 PyTorch 里是一行
`nn.MultiheadAttention(dim, n_head)`。把权重原样复制过去：

```text
两条输出的最大差值：1.02e-08
我们写的几十行，变成了一个 nn.MultiheadAttention(...)。里面做的事没有变：
三个投影 -> 拆头 -> 打分 -> 掩码 -> softmax -> 加权求和 -> 拼回来 -> 输出投影。
```

（唯一的区别是它把 Q、K、V 三个投影**拼成了一个矩阵** `in_proj_weight`，
所以要 `torch.cat` 一下才能把我们的三个权重放进去。）

### 实验四：同样两个模型，比时间和内存

```text
模型                参数量        引擎          毫秒/步     训练涨的内存
----------------------------------------------------------------
dim=128，4 层       800,292       我们的引擎    30          1882 MB
dim=128，4 层       800,292       PyTorch       25          118 MB
                                  倍数          1.2x        省下 94%
----------------------------------------------------------------
dim=192，6 层       2,678,436     我们的引擎    79          1975 MB
dim=192，6 层       2,678,436     PyTorch       51          167 MB
                                  倍数          1.5x        省下 92%
----------------------------------------------------------------
```

内存少用 92% 以上，速度只快 1.2–1.9 倍。

这个速度数字不好看，但它是真的，而且要如实说明：**在 CPU 上、模型这么小的时候，
PyTorch 并不会快到哪里去**——两边都是在调用同一批 numpy 级别的矩阵乘法，
瓶颈是 Python 的解释开销，不是数学。而且每一步只有几十毫秒，重复跑这个倍数会在
1.2 到 1.9 之间浮动；不过每一次跑，参数量更大的那一行倍数都更高 —— 差距是随规模长出来的。

真正拉开差距的是另外三件事，而它们没法用这张表量出来：

1. **内存**。我们的引擎每一步都要为整张计算图分配新的 float64 数组；
   PyTorch 在 backward 之后就把中间结果还掉了，而且用的是 float32。
2. **GPU**。`model.to("cuda")` 一行，上面这些矩阵乘法就跑到几千个核上去了。
   我们的引擎连想都不用想——它只有 numpy。
3. **每一个新算子的 backward**。第 9 章我们手写了 `exp`、`log`、`relu`、`tanh`、`gelu`、
   `softmax`、`masked_fill`……每一个都要自己推公式、自己验证。PyTorch 里有几百个算子，
   而且每一个都已经写好了。

## 新机制

这一章没有新的**模型机制**。模型一个字都没改。

这一章的新东西是：**换一个引擎，然后逐项确认"新引擎里的每个零件，都是我们自己写过的那个"。**

这就是 PyTorch 这类东西的真面目——一个**张量库 + 自动求导 + 一批标准零件**。
下面这张表是全章最重要的东西，建议对着代码看一遍：

| 我们自己写的（第 9–22 章） | PyTorch | 出现在哪一章 |
|---|---|---|
| `Tensor`、`.backward()`、`zero_grad()` | `torch.Tensor`、`autograd` | 第 9 章 |
| `no_grad()` | `torch.no_grad()` | 第 9 章 |
| `embedding(表, idx)`（按编号取行） | `nn.Embedding` | 第 10 章 |
| `x @ W + b` | `nn.Linear` | 第 3 章 |
| 第 22 章那份模型里，`x @ W`（投影不带偏置）、`LayerNorm` 在子层前面、输出层前不加 LN | `nn.Linear(bias=False)`、`x + self.attention(self.ln1(x))`、没有 `ln_f` | 第 14、18、22 章 |
| `layer_norm(x, w, b)` | `nn.LayerNorm` | 第 18 章 |
| 手写多头注意力（拆头 → 打分 → 掩码 → softmax → 拼回） | `nn.MultiheadAttention` | 第 14、15、21 章 |
| `masked_fill(mask, -1e9)` | `Tensor.masked_fill` | 第 21 章 |
| `cross_entropy(logits, targets)` | `F.cross_entropy` | 第 5、20 章 |
| `Adam(params, lr)` | `torch.optim.Adam` | 第 22 章 |
| 一个装着参数的类 + 手写的 `forward` | `nn.Module` + `forward` | 第 19、22 章 |
| 训练循环（zero_grad → backward → step） | 一模一样 | 第 22 章 |

有一点小差别值得单独记住：**`nn.Linear` 把权重存成 `(out, in)`**，
因为它算的是 `x @ W.T + b`；我们第 3 章写的是 `x @ W + b`，存的是 `(in, out)`。
所以从我们的模型往 PyTorch 搬权重的时候要转置一下（见 `after.py` 里的 `load_our_weights`）。
这只是"怎么存"，不是"怎么算"。

还有三个细节，是照着第 22 章原样搬过来的，写错了行为就变了，所以单独列出来：

| 第 22 章的写法 | 在 PyTorch 里怎么写 |
|---|---|
| 先 `LayerNorm(x)`，再进子层，最后 `x + 子层(...)`（第 18 章） | `x = x + self.attention(self.ln1(x), mask)` |
| 四个投影是 `x @ W`，没有偏置（第 14 章） | `nn.Linear(dim, dim, bias=False)` |
| 输出层前面**没有**最后那次 LayerNorm | 不要写 `self.ln_f` |

（第 25 章的 `tests/test_chapter_25.py` 里有两个测试专门钉住这三件事：
`test_参数表和第_22_章逐项对齐` 和 `test_归一化放在子层前面`。）

还有几个新名词，都是 PyTorch 这套东西的用语：

- **`nn.Module`**：一个"装参数的盒子"。只要把你的参数和 `forward` 放进去，
  它就自动知道怎么把所有参数列出来（`parameters()`）、怎么存到磁盘（`state_dict()`）、
  怎么切到推理模式（`eval()`）。
- **buffer**：模型里需要跟着模型走、但**不需要训练**的张量。我们的正弦位置编码表就是 buffer
  （`register_buffer`）——它得跟着模型一起存、一起搬到 GPU 上，但优化器不许动它。
- **dtype**：浮点数的精度。我们一直用 `float64`，PyTorch 默认 `float32`。
  一半的内存、更快的矩阵乘法，代价是小数点后少几位——这就是实验一里那个 `5.46e-08` 的来源。

## Python 实现

`after.py` 就是第 22 章的模型，一行一行换成了 PyTorch。对照着看最清楚。

**查表 + 位置**：

```python
self.tok_emb = nn.Embedding(vocab_size, dim)          # 第 10 章那张表
self.register_buffer("pos_table", torch.tensor(...))  # 第 16 章那张固定的表
...
x = self.tok_emb(idx) + self.pos_table[:length]
```

`nn.Embedding` 就是"按编号取行"，和我们的 `embedding(表, idx)` 完全一样。

**注意力**（手写版，因为这一版和我们的代码一一对应，最好对照）：

```python
q = split(self.Wq(x))                     # 第 14 章：我在找什么
k = split(self.Wk(x))                     # 第 14 章：你有什么
scores = q @ k.transpose(-1, -2) / math.sqrt(head_dim)
scores = scores.masked_fill(mask, float("-inf"))   # 第 21 章：不许看后面
weights = scores.softmax(dim=-1)
out = (weights @ v).transpose(1, 2).reshape(batch, length, dim)
return self.Wo(out)
```

把它换成 `nn.MultiheadAttention` 也可以，输出只差 `1e-08`（实验三）。

**Block**（和第 22 章逐行对应）：

```python
def forward(self, x, mask):
    x = x + self.attention(self.ln1(x), mask)                       # 第 17、18 章
    x = x + self.W2(torch.relu(self.W1(self.ln2(x))))               # 第 19 章
    return x
```

两个子层都是"**先归一化 → 再加工 → 再加回自己**"——这是第 18 章就定下来的顺序，
第 22 章原样用，这里也原样搬。投影那四个 `nn.Linear` 都带 `bias=False`，
因为第 14 章写的是 `x @ W`，没有偏置。

**训练循环**：和 `before.py` 逐行对应，只有求导那一行换了人。

```python
def train(model, steps, block_size, batch_size, lr, seed=0):
    optimizer = torch.optim.Adam(model.parameters(), lr=lr)
    ...
    for step in range(steps):
        x, y = get_batch(DATA, block_size, batch_size, rng)
        logits = model(x)
        loss = torch.nn.functional.cross_entropy(logits.reshape(-1, VOCAB_SIZE), y.reshape(-1))
        optimizer.zero_grad()
        loss.backward()          # before.py 里，这一行是我们自己写的
        optimizer.step()
```

跑 `after.py`，它还会做一件让人心里踏实的事：用第 23 章的方式生成一段文字。

```text
提示：床前明月光
续写：床前明月光疑是地上霜举头望明月低头思故乡春眠不觉晓处处闻啼
```

模型认出了这首诗。它是在 40 个字的语料上过拟合出来的，但至少说明**重写没有写坏**。

## 它解决了什么

- 同一份权重，两个引擎的前向输出最大差 `5.46e-08`，训练 100 步的 loss 曲线逐行相同
  （差值 `0.00000`）。**换引擎没有改变模型。**
- 同样一个 80 万参数的模型，训练时涨的内存从 1882 MB 降到 118 MB（省 94%）；
  270 万参数时从 1975 MB 降到 167 MB（省 92%）。
- 速度在 CPU 上只快 1.2–1.9 倍，但 PyTorch 可以 `.to("cuda")`，我们的引擎不行。
- 从这一章起，我们不用再为任何新算子手写 backward。

更重要的是那个感觉：`nn.Linear`、`nn.Embedding`、`nn.LayerNorm`、`nn.MultiheadAttention`
——这些名字看着唬人，拆开看，**每一个都是第 10 到 22 章里我们自己写过的东西**。
PyTorch 帮我们做了封装、加速、搬上 GPU，但它没有替我们发明任何机制。

## 它还解决不了什么

换完引擎，我们把第 22 章的模型原封不动搬到 PyTorch 上，它还是那个只会背诗的小东西。
因为**零件没变，规模也没变**——这一章我们只是终于有了能把规模做大的工具。

但有一个零件，现在看起来特别刺眼，而且它和规模无关。

回头看我们的分词：我们是一个字一个字喂给模型的。第 22 章的字表是 36 个字，
所以"床前明月光"是 5 个 token。

现在换一句第 1 章的话试试：

```text
苹果很好吃
```

"好吃"是一个词，我们喂进去的却是"好"和"吃"两个 token。
更麻烦的是这个：

```text
苹果不好吃
```

我们的字表里有"好"、有"吃"，但是**"不好"不是"好"加上什么**——
模型得自己学会"不"这个字会把后面那个字的判断翻过来。这在 36 个字的语料里根本学不到，
因为那个语料里连"不"都没有（古诗里出现的"不"是"不觉晓"里的"不"，
它和"甜不甜"的"不"是两回事）。

再往下想一步就更难受了：真实世界里每天都有新词——"平板"、"折叠屏"、"直播带货"。
我们的字表是**在训练之前就定死的**。碰到表外的字，模型只能吐出一个"我不认识"。

而这个字表，如果换成"词表"会怎么样？中文常用词有几百万个，
第 2 章那个"几万个 if"的噩梦会换一件衣服回来。

所以下一个问题是：**词表到底应该怎么定？为什么我们现在这种"一个字一个 token"的切法这么粗糙？**
